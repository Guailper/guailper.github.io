设计模式学习笔记：理解与 C++ 示例

发表于2026-05-06|更新于2026-05-06|C++设计模式

设计模式学习笔记：理解与 C++ 示例

设计模式不是固定模板，也不是背下来就能写出好代码的魔法。它更像是一组经过验证的“组织代码的经验”：当对象之间的关系开始变复杂时，设计模式帮助我们降低耦合、隔离变化、复用行为。

我理解设计模式时会先问三个问题：

  1. 这个模式想隔离哪一种变化？
  2. 它让谁依赖谁？
  3. 使用它之后，代码是更清晰了，还是只是多包了一层？

下面先补充一个常见的简单工厂，再按 GoF 经典 23 种设计模式整理。每个模式都包含：介绍、我的理解和一个简单 C++ 示例。

一、创建型模式

创建型模式关注“对象怎么创建”。当直接 new 对象会让业务代码依赖具体类，或者创建流程比较复杂时，可以考虑创建型模式。

1. 单例模式 Singleton

单例模式保证一个类在程序中只有一个实例，并提供一个全局访问点。常见场景有日志器、配置中心、线程池管理器等。

单例的核心不是“全局变量”，而是“唯一资源”。如果某个对象代表全局唯一状态，就可以考虑单例。但它也容易隐藏依赖关系，所以不要滥用。

C++ 示例

2. 简单工厂 Simple Factory

简单工厂不属于 GoF 23 种模式，但很常用。它把对象创建逻辑集中到一个工厂函数中，根据参数返回不同类型的对象。

简单工厂适合类型较少、变化不频繁的场景。它能把 new 从业务代码里拿走，但新增类型时通常要修改工厂函数。

C++ 示例

3. 工厂方法 Factory Method

工厂方法把对象创建延迟到子类中。父类定义创建接口，子类决定具体创建哪一种产品。

简单工厂是“一个工厂判断类型”，工厂方法是“不同工厂负责不同产品”。当新增产品时，可以新增工厂类，减少对原有工厂的修改。

C++ 示例

  1. 抽象工厂 Abstract Factory

抽象工厂用于创建一组相关对象。它提供多个创建接口，每个具体工厂负责创建同一产品族中的对象。

工厂方法关注“创建一个产品”，抽象工厂关注“创建一整套产品”。比如 Windows 风格的按钮和输入框应该成套出现，Mac 风格也应该成套出现。

C++ 示例

5. 建造者模式 Builder

建造者模式把复杂对象的构建过程拆成多个步骤，让同样的构建过程可以创建不同表示。

当构造函数参数太多，或者对象创建需要按步骤设置时，Builder 会比一个巨大构造函数更清晰。它尤其适合配置类、SQL 构造器、HTTP 请求构造器。

C++ 示例

6. 原型模式 Prototype

原型模式通过复制已有对象来创建新对象，而不是从头构造。

如果对象创建成本高，或者运行时才知道具体类型，原型模式很有用。C++ 中通常用虚函数 clone() 实现多态复制。

C++ 示例

二、结构型模式

结构型模式关注“类和对象如何组合”。它们通常用于解决接口不兼容、职责拆分、对象包装、层级组织等问题。

7. 适配器模式 Adapter

适配器模式把一个类的接口转换成客户端期望的另一个接口。

适配器像一个转换插头。老代码、第三方库、历史接口不方便改时，可以写一个适配器，让新代码按统一接口使用它。

C++ 示例

8. 桥接模式 Bridge

桥接模式把抽象部分和实现部分分离，让它们可以独立变化。

当一个类有两个变化维度时，不要用继承堆出一大堆组合类。桥接模式把其中一个维度抽出去，用组合代替继承。

C++ 示例

9. 组合模式 Composite

组合模式把对象组织成树形结构，使客户端可以用一致方式处理单个对象和对象集合。

组合模式适合“部分-整体”结构，比如文件系统、组织架构、UI 组件树。关键是让叶子节点和容器节点拥有同一个接口。

C++ 示例

10. 装饰器模式 Decorator

装饰器模式在不修改原类的情况下，动态地给对象增加功能。

装饰器本质是“套娃式增强”。它和继承都能扩展功能，但装饰器是在运行时组合行为，灵活性更高。

C++ 示例

11. 外观模式 Facade

外观模式为复杂子系统提供一个简单统一的入口。

外观不是为了隐藏所有细节，而是给常用流程提供一个更友好的 API。它能让调用方少知道一些内部模块的组合方式。

C++ 示例

12. 享元模式 Flyweight

享元模式通过共享对象来减少内存开销，适合大量对象拥有相同内部状态的场景。

享元的重点是区分内部状态和外部状态。可以共享的放到享元对象里，不可共享的由调用方传入。

C++ 示例

13. 代理模式 Proxy

代理模式为真实对象提供一个替身，用于控制访问、延迟加载、权限检查或缓存。

代理和装饰器都包了一层对象，但目的不同：装饰器偏向增强功能，代理偏向控制访问。

C++ 示例

三、行为型模式

行为型模式关注“对象之间如何协作”。它们常用于解耦请求发送者和接收者，或者把算法、状态、操作封装成独立对象。

14. 责任链模式 Chain of Responsibility

责任链模式把多个处理者串成一条链，请求沿链传递，直到某个处理者处理它。

它适合审批流、过滤器、日志处理等场景。调用方不需要知道最终是谁处理请求，只要把请求交给链头即可。

C++ 示例

15. 命令模式 Command

命令模式把请求封装成对象，使请求可以被存储、排队、撤销或重做。

命令模式把“要做什么”从调用者那里抽出来。按钮、菜单、任务队列、撤销系统都很适合使用它。

C++ 示例

16. 解释器模式 Interpreter

解释器模式为某种语言或表达式定义语法表示，并提供解释执行的方法。

它适合规则简单、语法稳定的小型 DSL。复杂语言不要手写解释器，应该使用成熟解析器工具。

C++ 示例

17. 迭代器模式 Iterator

迭代器模式提供一种顺序访问集合元素的方法，而不暴露集合内部结构。

C++ 标准库中的迭代器就是典型例子。它让算法可以操作不同容器，只要容器提供统一迭代接口。

C++ 示例

18. 中介者模式 Mediator

中介者模式用一个中介对象封装多个对象之间的交互，避免对象之间直接互相引用。

当多个对象之间互相调用形成网状关系时，中介者可以把复杂关系收拢到一个中心。代价是中介者本身可能变得很复杂。

C++ 示例

19. 备忘录模式 Memento

备忘录模式在不暴露对象内部细节的情况下保存和恢复对象状态。

备忘录常用于撤销、快照、游戏存档。它的关键是状态由原对象创建和恢复，外部只负责保存快照。

C++ 示例

20. 观察者模式 Observer

观察者模式定义对象之间的一对多依赖。当被观察对象状态变化时，所有观察者都会收到通知。

观察者适合事件通知、消息订阅、GUI 回调等场景。它能让发布者不依赖具体订阅者。

C++ 示例

21. 状态模式 State

状态模式把对象在不同状态下的行为封装到独立状态类中，使对象看起来像是在状态改变时改变了行为。

如果代码里出现大量 if (state == xxx)，而每种状态下行为差异明显，就可以考虑状态模式。

C++ 示例

22. 策略模式 Strategy

策略模式定义一组算法，把每个算法封装起来，并让它们可以互相替换。

策略模式解决的是“算法可替换”。它和状态模式结构很像，但意图不同：策略通常由外部选择，状态通常由对象内部状态变化驱动。

C++ 示例

23. 模板方法 Template Method

模板方法在父类中定义算法骨架，把某些步骤延迟到子类实现。

模板方法适合流程稳定、步骤可变的场景。父类控制整体流程，子类只改局部步骤。

C++ 示例

24. 访问者模式 Visitor

访问者模式把作用于对象结构中的操作封装成访问者，使得可以在不修改元素类的情况下增加新操作。

访问者适合对象结构稳定、操作经常变化的场景。它把“数据结构”和“作用在结构上的操作”分开，但代码会变得比较绕。

C++ 示例

四、迭代补充：模式之间的区别

很多模式的代码结构看起来相似，真正区别在“意图”。

模式 容易混淆的模式 区别
工厂方法 抽象工厂 工厂方法创建一个产品，抽象工厂创建一组产品
装饰器 代理 装饰器增强功能，代理控制访问
策略 状态 策略由外部选择算法，状态由内部状态驱动行为变化
适配器 外观 适配器解决接口不兼容，外观简化复杂子系统
组合 装饰器 组合管理树形层级，装饰器包装单个对象

五、学习设计模式时的注意点

  1. 先写出直接代码，再观察变化点，不要一开始就套模式。
  2. 模式是为了解耦变化，不是为了增加类的数量。
  3. C++ 中要注意对象生命周期，示例里优先使用 std::unique_ptr 和 std::shared_ptr 管理资源。
  4. 学习时要看“模式解决的问题”，不要只背 UML 图。
  5. 如果一个模式让当前代码更难读，就说明它可能还不是必要的。

六、总结

设计模式的价值在于帮助我们识别代码中的稳定部分和变化部分：

  • 创建型模式处理对象创建的变化。
  • 结构型模式处理对象组合的变化。
  • 行为型模式处理对象协作和算法流程的变化。

真正掌握设计模式，不是看到需求就立刻套模板，而是在代码出现重复判断、复杂依赖、变化扩散时，能想到一种更清晰的组织方式。
